Las cuatro capas y su única regla

Todo el orden del proyecto se sostiene en una sola regla, la regla de dependencia: las flechas de import solo apuntan en una dirección — ui → state → data → domain — y domain no apunta a nadie. Viniendo de React: es la misma disciplina de "los componentes no hacen fetch, llaman hooks; los hooks llaman servicios", pero con nombre y apellido.

domain/ — el vocabulario

Entidades y tipos puros: Product, User, Token, AuthState. Es el idioma que hablan las demás capas.

  • ✓ clases inmutables, enums, copyWith
  • ✓ lógica propia del negocio (ej. felCode, priceLabel)
  • ✗ imports de dio, riverpod, flutter — de nada

Test rápido: ¿compilaría en un script de Dart puro sin Flutter? Debe ser sí.

data/ — cómo se obtienen los datos

Habla con el mundo exterior (HTTP, Keychain, mañana SQLite) y devuelve tipos de domain.

  • ✓ APIs (AuthApi, ProductApi): HTTP puro, sin estado
  • ✓ Repositorios (AuthRepository): combinan fuentes (API + storage)
  • ✓ Storage (SecureStore)
  • ✗ saber de widgets, de navegación o de estado de UI

state/ — la orquestación

Estado vivo de la app y las operaciones que lo mutan. Traduce eventos de UI en llamadas a data y publica el resultado.

  • ✓ Notifiers (AuthController, ProductListNotifier)
  • ✓ providers.dart: la raíz de composición (ver abajo)
  • ✗ construir widgets, formatear para pantalla

ui/ — pintar y delegar

Widgets que hacen watch del estado y llaman métodos del notifier. Nada más.

  • ✓ pantallas, cards, skeletons, animaciones
  • ✓ estado efímero de widget (un controller de texto, un flag de loading local)
  • ✗ tocar data/ directamente — regla de oro
★ Insight. La recompensa de esta regla no es elegancia: es que cada capa se puede reemplazar sin tocar las demás. Cuando llegue drift (curso 08), solo data/ cambia. Cuando rediseñemos la UI (curso 05), solo ui/ cambia. Ese es el contrato que convierte esto en un template.

providers.dart: la raíz de composición

Tu intuición fue correcta: hay un solo Dio con la URL base y el interceptor, y de ahí se inyecta en AuthApi y ProductApi. A ese archivo donde se arma todo el grafo de objetos se le llama raíz de composición (composition root): es el único lugar del proyecto que sabe cómo se conecta todo. En React es el equivalente a ese archivo donde componés los providers de contexto + el cliente de fetch configurado.

lib/state/providers.dart (anotado) 
// 1. La pieza compartida se crea UNA vez…
final dioProvider = Provider<Dio>((ref) {
  final store = ref.watch(secureStoreProvider);   // ← dependencia declarada
  final dio = Dio(BaseOptions(baseUrl: kBaseUrl, ...));
  dio.interceptors.add(/* Bearer + (pendiente) refresh */);
  return dio;
});

// 2. …y quien la necesita la PIDE, no la construye:
final authClientProvider = Provider<AuthApi>(
  (ref) => AuthApi(ref.watch(dioProvider)),        // inyección
);
final productApiProvider = Provider<ProductApi>(
  (ref) => ProductApi(ref.watch(dioProvider)),     // misma instancia de Dio
);

// 3. El repositorio combina dos fuentes — también pedidas:
final authRepositoryProvider = Provider<AuthRepository>(
  (ref) => AuthRepository(
    api: ref.watch(authClientProvider),
    store: ref.watch(secureStoreProvider),
  ),
);
★ Insight. Fíjate que AuthApi recibe Dio por constructor y no llama a Riverpod por dentro. Eso significa que la clase se puede testear pasándole un Dio falso, sin levantar ningún provider. La regla: las clases de data/ no saben que Riverpod existe; solo la raíz de composición las conecta. Por eso los providers "de data" pueden vivir en state/providers.dart sin romper capas: la declaración del cableado es orquestación, aunque los objetos cableados sean de data.

El flujo de seguridad, de punta a punta

Este es el viaje del token con lo que existe hoy, incluyendo lo que ya verifiqué en tu API Go (tokens.go, main.go). Los chips marcan qué está resuelto y qué queda pendiente — los pendientes son exactamente el temario del Curso 03.

  1. Credenciales viajan al servidor OK

    LoginScreen → AuthController.login() → AuthRepository → AuthApi → POST /auth/login. La pantalla nunca ve un token; solo conoce al controller. Hoy viaja por HTTP local; TLS real vía Tailscale llega en el curso 09.

  2. Go firma un par de tokens OK

    HS256 con claims propios: access (15 min) y refresh (7 días), distinguidos por el claim typ — un refresh no sirve como access ni al revés. Cada token lleva jti único (la puerta a revocación futura) y el parser rechaza cualquier algoritmo que no sea HMAC (corta el ataque alg=none).

  3. El par se guarda cifrado en el dispositivo OK

    AuthRepository.login() → SecureStore.saveTokens() → Keychain (iOS) / Keystore (Android). Nunca SharedPreferences, nunca memoria plana.

  4. El guard del router libera la navegación OK

    AuthState pasa a authenticated → el redirect de GoRouter (conectado vía refreshListenable) reevalúa toda navegación. Tres estados: unknown (restaurando sesión), unauthenticated (→ /login), authenticated (→ app). Navegación directa sin sesión: imposible.

  5. Cada request lleva el Bearer automáticamente OK

    El interceptor onRequest del Dio único lee el access de SecureStore y agrega Authorization: Bearer …. Ninguna pantalla ni API lo hace a mano — heredan la seguridad por usar el mismo Dio.

  6. El middleware Go valida y contextualiza OK

    authMiddleware verifica firma + expiración + typ == "access" y mete el user id en el contexto del request. Los handlers nunca re-parsean tokens.

  7. Access vencido → refresh silencioso PENDIENTE · curso 03

    El onError del interceptor tiene el TODO: ante un 401, pedir POST /auth/refresh con un Dio "pelado" (sin interceptor, para no entrar en loop), guardar el par nuevo y reintentar la request original. El server ya lo soporta y AuthApi.refresh() ya existe — falta solo el eslabón del interceptor. Hoy: a los 15 minutos la sesión "muere" en silencio.

  8. Restaurar sesión al abrir la app PENDIENTE · curso 03

    restore() valida la sesión con GET /auth/me usando el access. Si el access venció (y vence cada 15 min), te desloguea aunque el refresh siga vivo 7 días. Con el paso 7 resuelto, este se arregla casi solo.

  9. Logout OK (local)

    SecureStore.clear() borra el par del dispositivo. Revocación del lado del servidor (lista de jti revocados) es opcional y quedaría para Seguridad II si el ERP lo amerita.

  10. Cert pinning EN EVALUACIÓN · curso 09

    Mi evaluación: pinnear hoy no aporta — no hay TLS que pinnear en localhost, y dentro de la tailnet el tráfico ya viaja cifrado por WireGuard. El momento correcto es el curso 09, cuando expongamos el API con tailscale serve (certificados reales de Let's Encrypt) y el iPhone consuma HTTPS: ahí pinneamos SPKI (la clave pública, no el certificado, que rota cada ~90 días) con backup pin. El TODO(cert-pinning) ya está marcado en el lugar exacto: dioProvider.

La decisión: layer-first vs feature-first

Hoy el proyecto agrupa por capa (layer-first): toda la UI junta, todo el estado junto. Con 3 features y 21 archivos funciona perfecto. Pero el destino de este template es un ERP: clientes, almacenes, series, formas de pago, transacciones, ventas… Con 8+ módulos, layer-first obliga a saltar entre 4 carpetas lejanas para tocar una sola feature. La alternativa es agrupar por feature y dejar lo transversal en core/:

hoy: layer-first 
lib/
├─ domain/    product.dart, auth.dart
├─ data/      auth_api.dart, product_api.dart,
│             auth_repository.dart, secure_store.dart
├─ state/     providers.dart, auth_controller.dart,
│             product_list_controller.dart, clock.dart
├─ ui/        login_screen.dart, home_screen.dart,
│             live_screen.dart, products/…
├─ router.dart · theme.dart · main.dart
propuesta: feature-first 
lib/
├─ core/                 ← lo transversal
│  ├─ network/           dio_provider.dart
│  ├─ storage/           secure_store.dart
│  ├─ router/            router.dart
│  └─ theme/             theme.dart
├─ features/
│  ├─ auth/
│  │  ├─ domain/ data/ state/ ui/
│  ├─ products/
│  │  ├─ domain/ data/ state/ ui/
│  └─ live/
└─ main.dart

Las capas y su regla de dependencia no cambian — solo cambia el criterio de agrupación: cada feature contiene sus propias cuatro capas en miniatura. Son 21 archivos (~1 hora de mover + arreglar imports); en el curso 10, con el dominio ERP encima, sería un día entero y con más riesgo.

★ Decisión (2026-07-12): feature-first, ahora. "Ahora corregirlo no duele tanto" aplicada a su primer caso real. La ejecución completa está en la hoja de ruta, abajo. Nota importante: al migrar, providers.dart se disuelve — cada provider se declara junto a la clase que provee (patrón idiomático de Riverpod moderno). La raíz de composición deja de ser un archivo y pasa a ser el grafo mismo.

import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_secure_storage/flutter_secure_storage.dart';

class SecureStore {
  static const _s = FlutterSecureStorage();

  Future<void> saveTokens(String access, String refresh) async {
    await _s.write(key: 'access', value: access);
    await _s.write(key: 'refresh', value: refresh);
  }

  Future<String?> readAccess() => _s.read(key: 'access');
  Future<String?> readRefresh() => _s.read(key: 'refresh');
  Future<void> clear() => _s.deleteAll();
}

final secureStoreProvider = Provider<SecureStore>((ref) => SecureStore());

import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:mini_flutter/core/storage/secure_store.dart';

/// Ejercicio 3: la URL ya no vive en el código — llega por --dart-define.
///   flutter run --dart-define=API_URL=http://10.0.2.2:9090        (Android emu)
///   flutter run --dart-define=API_URL=https://mac.tailnet.ts.net  (iPhone/tailnet)
/// Sin flag cae al default de desarrollo (iOS sim / macOS).
const kBaseUrl = String.fromEnvironment(
  'API_URL',
  defaultValue: 'http://localhost:9090',
);

/// Dio compartido: baseUrl + interceptor Bearer, creado UNA vez.
final dioProvider = Provider<Dio>((ref) {
  final store = ref.watch(secureStoreProvider);
  final dio = Dio(
    BaseOptions(baseUrl: kBaseUrl, connectTimeout: const Duration(seconds: 10)),
  );

  dio.interceptors.add(
    InterceptorsWrapper(
      onRequest: (options, handler) async {
        final t = await store.readAccess();
        if (t != null) {
          options.headers['Authorization'] = 'Bearer $t';
        }
        handler.next(options);
      },
      onError: (error, handler) async {
        if (error.response?.statusCode == 401) {
          // Curso 03: refresh con un Dio "pelado". NUNCA importando
          // features/auth aquí — la flecha no apunta hacia atrás.
        }
        handler.next(error);
      },
    ),
  );

  // TODO(cert-pinning): al pasar a HTTPS real (curso 09), pinnear SPKI acá.
  return dio;
});
