Curso 02 · fundamentos

Riverpod a fondo

El grafo reactivo: qué hacen realmente ref.read, watch y listen; el catálogo completo de providers del template; y lo nuevo de la v3 que te va a sorprender.

El modelo mental: el grafo vive fuera del árbol

En React, el estado vive dentro del árbol de componentes: un hook pertenece a su componente, un contexto a su subárbol. Riverpod invierte eso: los providers forman un grafo de dependencias que vive fuera del árbol de widgets (dentro del ProviderScope que envuelve tu app en main.dart). Los widgets no "contienen" estado global — se enchufan a nodos del grafo.

React (Gibbor) 
// el estado pertenece al árbol
<AuthProvider>        ← contexto atado al subárbol
  <Products />        ← useQuery vive en el componente
</AuthProvider>
Riverpod (mini_flutter) 
// el grafo existe aparte; los widgets se enchufan
dioProvider ← productApiProvider ← productListProvider
                                         ↑ watch
                              ProductListScreen (widget)

Ya viste este grafo completo en el diagrama del curso 01. La consecuencia práctica: un provider puede depender de otro provider (con el mismo ref), y la invalidación se propaga sola por el grafo — sin prop-drilling, sin context hell.

Tu recuerdo, auditado

Esto fue lo que recordabas. Veredicto línea por línea:

Lo que recordabasVeredictoLa versión precisa
"ref.read → un solo valor" casi ref.read es una lectura puntual sin suscripción: te da el valor de ahora y no te entiendes más. No es que devuelva "un" valor — es que no te avisa cuando cambie. La docs oficial además pide: si puedes usar watch, prefiere watch.
"ref.watch y ref.listen → me suscribo a los cambios" correcto Ambos se suscriben, pero reaccionan distinto: watch reconstruye (el widget o el provider que lo llama); listen ejecuta un callback (previous, next) sin reconstruir — para efectos: toasts, navegación, logs.
"provider → devuelve el state (AuthState); provider.notifier → los métodos (login/logout)" correcto Tal cual: watch(authControllerProvider) → AuthState; read(authControllerProvider.notifier) → la instancia de AuthController con sus métodos (y llamarla nunca reconstruye nada por sí mismo — reconstruye lo que esté watching el estado que el método mute).

Nota fina: los métodos viven en el controller (AuthController), no en el repositorio — en tu ejemplo dijiste "AuthRepositoryProvider", pero a los repositorios nunca les hablamos desde la UI.

Los tres verbos, en vivo

Tres "widgets" enchufados al mismo authProvider simulado, cada uno con un verbo distinto. Pulsa login() / logout() y observa quién reacciona y cómo (el flash ámbar = rebuild):

demo · watch vs read vs listen

ref.watch(authProvider)
—
rebuilds: 0
ref.read(authProvider) · leído en build
—
rebuilds: 0
ref.listen(authProvider, (prev, next) ⇒ …)
no muestra estado — dispara efectos

Lo que hay que ver: ① watch se reconstruye con cada cambio. ② read se queda con el valor de cuando se construyó — solo se actualiza si algo más lo reconstruye (tercer botón). Ese desfase silencioso es el bug clásico de usar read donde iba watch. ③ listen no se reconstruye: recibe (previous, next) y hace su efecto.

★ Insight. La docs define watch literalmente como listen + invalidarse a sí mismo: listen(provider, (_, __) => invalidateSelf()); return sub.read();. O sea: los tres verbos son el mismo mecanismo de suscripción con distinta reacción — reconstruirse (watch), callback (listen), o ninguna (read).

¿Dónde es legal cada verbo?

build de widget / cuerpo de providercallbacks (onPress, métodos del notifier)
watch ✅ el lugar correcto — declara dependencias 🚫 lanza error: no hay nada que reconstruir después
read ⚠️ compila, pero crea el desfase de la demo — evítalo ✅ el lugar correcto — acción puntual
listen ✅ en la raíz del build (widgets) o en build de notifiers 🚫 se registraría un listener por cada tap

Regla nemotécnica: watch para construir, read para actuar, listen para reaccionar. En React: watch ≈ suscripción de un hook, read ≈ leer un ref.current, listen ≈ useEffect con dependencia.

El catálogo: los providers de tu template

Todos los tipos que ya usas, con su ejemplo real:

TipoEn el templatewatch devuelveÚsalo para
Provider<T> dioProvider, authApiProvider, authRepositoryProvider, productApiProvider, goRouterProvider T directo Objetos que se construyen una vez y se derivan de otros: infraestructura, servicios. Sin estado mutable propio.
NotifierProvider authControllerProvider el estado (AuthState) Estado síncrono mutable con métodos. El notifier es la única puerta de mutación.
AsyncNotifierProvider productListProvider AsyncValue<List<Product>> Estado que nace de una operación async y además tiene métodos (refresh, y pronto create/update).
FutureProvider (.family) productProvider(id) AsyncValue<Product> Lecturas async sin métodos. .family lo parametriza: cada id es un nodo distinto del grafo, con caché propio.
StreamProvider clockProvider AsyncValue<DateTime> Fuentes que emiten muchas veces. El caso fuerte (SSE de inventario) llega en el curso 07.
★ Insight. Fíjate el patrón: todo lo async llega a la UI como AsyncValue<T> — loading/data/error como datos, no como excepciones ni banderas sueltas. Tu ProductListScreen ya lo explota con .when(...). En React esto es lo que te da React Query con isLoading/data/error, pero aquí es un tipo sellado del lenguaje: el compilador te obliga a manejar los tres casos.

Notifier por dentro (y un mito de tu código)

Dos hechos de la docs que ordenan todo: ① build() se re-ejecuta cuando cambia una dependencia observada con watch, pero la instancia del notifier se preserva (sus campos sobreviven). ② Dentro de build() es seguro y preferible usar ref.watch; en los métodos (como refresh()) va ref.read.

Y aquí el mito: tu product_list_controller.dart tiene un comentario que dice "Dentro de métodos/build usás ref.read (no watch): no querés re-suscribir acá". Para métodos: cierto. Para build(): falso — es exactamente el lugar donde watch declara dependencias. Hoy no te muerde porque productApiProvider nunca cambia, pero el comentario te enseñaría el hábito equivocado cada vez que lo leas. Lo corriges en el ejercicio 2.

Detalles que te ahorrarán sustos:

  • En un Notifier síncrono, leer state dentro de build() antes de asignarlo lanza excepción (aún no existe). AsyncNotifier no sufre esto: arranca en AsyncLoading solo.
  • AsyncValue.guard(fn) = el try/catch idiomático: éxito → AsyncData, excepción → AsyncError. Ya lo usas en refresh().
  • ¿Necesitas el valor resuelto de un provider async dentro de otro? await ref.watch(provider.future) — lo usaremos en el curso 03.

Modificadores: family y autoDispose

.family ya lo dominas (curso 01). El que te falta es .autoDispose, y un dato importante de la v3 con providers declarados a mano: no es el default — tus providers viven para siempre salvo que lo pidas. ¿Consecuencia hoy? Cada productProvider(id) que visitas queda cacheado en memoria indefinidamente: visita 200 detalles y tienes 200 productos vivos.

Con .autoDispose, el nodo se destruye cuando nadie lo observa — y trae dos herramientas finas, directas de la docs oficial:

final myProvider = FutureProvider.autoDispose((ref) async {
  final cancelToken = CancelToken();
  ref.onDispose(() => cancelToken.cancel()); // ① sales de la pantalla → se cancela el HTTP

  final response = await dio.get('path', cancelToken: cancelToken);
  ref.keepAlive();                            // ② si llegó bien, consérvalo en caché
  return response;
});

El patrón completo es elegante: si el usuario abre y cierra la pantalla a mitad de la request, la request se cancela (①); pero si la data ya llegó, keepAlive() la conserva aunque salgas (②). Cache con límites, sin bibliotecas extra.

Nuevo en v3: el retry automático (te va a pasar)

Riverpod 3 reintenta solo los providers async que fallan: 10 reintentos, arrancando en 200 ms y doblando hasta 6.4 s (ignora errores de programación y excepciones re-lanzadas entre providers). Esto es nuevo — en la v2 no existía.

Implicación práctica en TU app: si el API Go está caído, productListProvider no muestra el ErrorView al primer fallo — el skeleton se queda ~13 segundos reintentando en silencio antes de rendirse. Para un template production-grade eso puede ser justo lo que quieres (resiliencia gratis)… o un UX confuso (usuario mirando un shimmer eterno). Se controla por provider: 

final productListProvider =
    AsyncNotifierProvider<ProductListNotifier, List<Product>>(
      ProductListNotifier.new,
      retry: (retryCount, error) => null, // null = no reintentar
      // o una política propia:
      // retry: (n, e) => n < 3 ? Duration(milliseconds: 500 * n) : null,
    );

En el ejercicio 3 lo vas a ver antes de decidir la política del template.

Bonus: select, el bisturí de watch

watch reconstruye ante cualquier cambio del estado observado. select lo afina: observa solo una proyección. 

// HomeScreen se reconstruye ante CUALQUIER cambio de AuthState:
final auth = ref.watch(authControllerProvider);

// Con select, solo si cambia el email:
final email = ref.watch(
  authControllerProvider.select((s) => s.user?.email),
);

Es el equivalente a los selectores de Zustand/Redux. Con estados pequeños como AuthState es micro-optimización; con el dominio ERP (curso 10) será higiene básica.

Ejercicios (tú escribes)

Ejercicio 1 · autoDispose + cancelación en el detalle de producto

Predicción antes de tocar nada: con el código actual, si abres el detalle del producto A, vuelves, y entras al del producto B… ¿cuántas instancias de Product quedan vivas en el grafo? ¿Y después de visitar 50?

Luego, en product_detail_controller.dart, aplica el patrón completo:

import 'package:dio/dio.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:mini_flutter/features/products/data/product_api.dart';
import 'package:mini_flutter/features/products/domain/product.dart';

/// autoDispose: el detalle se destruye al salir de la pantalla…
/// …salvo que la carga haya terminado bien (keepAlive) → caché con límites.
final productProvider = FutureProvider.autoDispose
    .family<Product, String>((ref, id) async {
  final cancelToken = CancelToken();
  ref.onDispose(cancelToken.cancel); // si sales a mitad de carga, se cancela

  final product = await ref
      .watch(productApiProvider)
      .get(id, cancelToken: cancelToken);

  ref.keepAlive(); // llegó bien → consérvalo aunque salgas
  return product;
});

Esto pide un cambio pequeño en ProductApi.get para aceptar el token:

Future<Product> get(String id, {CancelToken? cancelToken}) async {
  final res = await _dio.get('/products/$id', cancelToken: cancelToken);
  return Product.fromJson(res.data as Map<String, dynamic>);
}

Ejercicio 2 · Derribar el mito del comentario

En product_list_controller.dart: build() debe declarar su dependencia con watch; los métodos siguen con read. Y el comentario engañoso se va:

class ProductListNotifier extends AsyncNotifier<List<Product>> {
  @override
  Future<List<Product>> build() {
    // build: watch — declara la dependencia (si la API cambiara, rebuild).
    final api = ref.watch(productApiProvider);
    return api.list();
  }

  /// Reintento / pull-to-refresh.
  Future<void> refresh() async {
    state = const AsyncLoading();
    // métodos: read — acción puntual, sin re-suscribir.
    state = await AsyncValue.guard(
      () => ref.read(productApiProvider).list(),
    );
  }
}

Ejercicio 3 · Ver el retry automático con tus propios ojos

Experimento, sin tocar código todavía: ① apaga el API Go, ② abre el listado de productos, ③ cronometra cuánto vive el skeleton antes del ErrorView, ④ enciende el API y dale retry. Predicción: ¿~cuántos segundos medirás? (la respuesta sale de la política por defecto descrita arriba).

Después decide y aplica la política del template en productListProvider (mi recomendación para datos de lectura: 2–3 reintentos rápidos y rendirse — el pull-to-refresh ya le da al usuario su propio botón de reintentar). Documenta tu decisión con un comentario junto al retry:.

Ejercicio 4 (bonus) · select en HomeScreen

Cambia el watch de HomeScreen para observar solo el email con select. Es un cambio de una línea — el valor está en que veas que el resto de la pantalla deja de depender del AuthState completo.

★ Insight final. Si miras los cuatro ejercicios juntos, son la misma lección: en Riverpod, el rendimiento y la corrección se deciden en la declaración de dependencias — qué observas (watch/select), cuánto vive (autoDispose/keepAlive) y cómo falla (retry/guard). El código de negocio casi no cambia; cambia el contrato con el grafo.
